Implement the following change in the EXISTING DealFlow360 customer registration/activation flow.

IMPORTANT:
- Do NOT create a new authentication system.
- Do NOT create a second token system.
- Use the EXISTING customer activation/login token flow.
- Preserve the existing JWT login system.
- Preserve the existing customer activation mechanism.
- Do NOT redesign unrelated frontend pages.
- Use the existing Node.js + Express + PostgreSQL architecture.
- Use the existing React frontend architecture.
- Inspect the existing code before changing anything.

==================================================
GOAL
==================================================

When an Admin helps a customer register/activate their DealFlow360 account, the Admin already has the customer's email address.

The system must:

1. Generate the customer's activation/login token in the BACKEND.
2. Display the generated token to the Admin.
3. Send the same token to the customer's provided email address.
4. Store only a HASHED version of the token in the database.
5. Preserve the existing token expiry/security behavior.
6. Customer must use the emailed/displayed token through the existing activation flow.

The flow should be:

Admin
  ↓
Customer registration/activation form
  ↓
Customer email entered
  ↓
Backend generates activation token
  ↓
 ┌───────────────────────────────┐
 │                               │
 ↓                               ↓
Admin receives token       Customer receives email
 │                               │
 └───────────────┬───────────────┘
                 ↓
        Existing activation flow
                 ↓
        Customer sets password
                 ↓
        Customer logs in
                 ↓
             JWT issued

==================================================
2. BACKEND GENERATES TOKEN
==================================================

The backend must generate the raw customer activation token.

The frontend must NEVER generate the token.

Example:

Admin submits:

{
  customerId: 12,
  email: "customer@example.com"
}

Backend:

1. Validate admin authentication/authorization.
2. Validate customer exists.
3. Validate email.
4. Generate cryptographically secure activation token.
5. Hash token.
6. Store hashed token in the existing activation-token field.
7. Store/update expiry.
8. Return the raw token in the API response for Admin display.
9. Send the raw token to the customer's email.

The raw token must never be stored in PostgreSQL.

==================================================
3. TOKEN RESPONSE TO ADMIN
==================================================

The API response should contain the raw token because the Admin explicitly needs to provide it to the customer.

Example:

{
  "message": "Customer activation token generated successfully",
  "customer": {
    "id": 12,
    "name": "Quantum Logistics Group",
    "email": "customer@example.com"
  },
  "activationToken": "DF360-8K4P-29XM",
  "expiresAt": "..."
}

Do not expose the hashed token.

Do not return unnecessary sensitive database fields.

==================================================
4. EMAIL THE SAME TOKEN
==================================================

Use the same raw token generated by the backend and send it to the customer's provided email.

DO NOT generate a second token for the email.

The flow must be:

const rawToken = generateToken();

const hashedToken = hash(rawToken);

save(hashedToken);

sendEmail(rawToken);

returnToAdmin(rawToken);

Therefore:

Admin token = Customer email token

Both must be identical.

9. EMAIL FAILURE BEHAVIOR
==================================================

This needs careful handling.

The system should not silently tell the Admin:

"Email sent successfully"

if the email actually failed.

Use a clear response/state.

Preferred behavior:

Generate token
    ↓
Persist hashed token
    ↓
Attempt email
    ↓
If successful:
    Return success + token
    Show "Email sent"

If email fails:
    Return an appropriate error/state such as:

{
  "message": "Customer activation token generated, but email delivery failed.",
  "activationToken": "...",
  "emailSent": false
}

The Admin should still be able to see/copy the token so the registration process is not unnecessarily blocked.

However, do not log the raw token unnecessarily on the server.

13. SECURITY
==================================================

The following rules are mandatory:

- Raw token is never stored in DB.
- Raw token is never logged unnecessarily.
- Raw token is never included in unrelated API responses.
- Raw token is only returned by the specific Admin activation endpoint because the Admin needs it.
- Customer must receive the same raw token by email.
- Token must have an expiry.
- Previous token must be invalidated when a new one is generated.
- Endpoint must require Admin authorization.
- A normal Sales Rep/Manager/Finance user must not be able to generate arbitrary customer activation tokens.
- Validate that the customer exists.
- Validate that the email belongs to the customer/registration request.
